## 3. “雷视协同”的真实代码范围

### 3.1 功能语义

当前实现为：雷达提供目标位置、距离和跟踪；相机提供人物检测与短期视觉轨迹；操作者人工核对并关联两路目标；可选严格视觉保护控制运动许可。

它没有实现几何标定、视觉深度测量或自动雷视身份匹配。`cooperative_view.hpp:15`、`cooperative_view.hpp:28` 与 `camera_association.hpp` 的注释明确说明了这一点。重组时应保持这些语义，避免在 UI/文档中改称自动融合定位。

### 3.2 主调用链

```text

    → UdpListener：ADC 接收、组帧、处理与结果传输
      → DSP：CPU/CUDA FFT → CFAR → DoA → 点云

      → CameraWorker：V4L2、YOLO11/OpenCV DNN

      → CameraRecorder：图像与事件记录

      → my_radar_follower.gui_runtime
        → 底盘进程 / odom_receiver / txt_tracker_bridge
          → /cmd_vel
```

## 4. 审阅发现与清理风险

### R1：不能仅保留 cooperative_view 文件，或直接删除独立传感器实现

位置：`radar_gui.cpp:530–600`，尤其 `567–589`。

三个页面共用同一个雷达控件与 `CameraAssistPanel`。`mountSensors` 在切页时重新挂载它们，并非各有一份传感器实现。现有 `tests/cooperative_layout_test.cpp:302` 也验证只存在一个相机面板。

实施要求：固定把这两个共享控件挂在协同页，删除独立页面容器和切页重挂载逻辑。保留实际雷达绘制、相机采集、目标选择及状态同步代码。同步修改 `cooperative_layout_test.cpp:274` 中“三个页签”的断言。

### R2：reference 是当前默认构建的硬依赖

位置：`CMakeLists.txt:48–64`。

`replay_v1`、`replay_v2` 无条件引用 `reference/YDS-V12/`、`reference/V2-current/`；即使关闭 GUI 或测试，仍会配置这些目标。直接删除 `reference/` 会使 CMake 配置失败。

此外，`replay_radar` 和 `replay_v3` 使用同一源文件并链接同一组库，当前是重复构建的两个名称。

实施要求：先让历史比较目标退出默认构建，消除脚本、条件 include 与测试引用，再归档历史实现。保留一个当前回放目标；`recording_index_cli` 等测试必须改为引用该目标。历史版本需要留证时应整体归档源码、比较脚本及说明，不能只删一部分。

### R3：界面来源存在维护分叉

位置：`radar_gui.cpp:6,186,459`；`CMakeLists.txt:161–169`；`ui_radar_gui_v2.h` 文件头。

当前编译直接 include 根目录生成头，CMake 只配置了 AUTOMOC，未配置 AUTOUIC，也未把 `.ui` 纳入自动生成流程。运行时又通过 `setupWorkspaceLayout()` 重建布局。因此编辑 `.ui` 不会自动更新现有生成头，旧布局和运行时布局也容易不同步。

实施要求：采用一个明确来源。建议保留 Qt Designer 表单中的基础控件，以 AUTOUIC 在构建目录生成头；协同布局使用一个专门的组装函数/组件。生成可复现后，删除根目录受维护的生成头。不得先删头文件再处理构建。

### R5：重复配置不能立即删，构建入口也需要统一

- 根目录和 `config/` 中的 `IWR6843_260714-15m-10Hz-9.8cm.cfg` SHA-256 完全相同：`EB9F57E2B82B7F42385D907C5A40B6C56B5B77CD4350885C388274A418DAE0CF`。

### R6：已确认的代码问题——相机 probe 会意外录制

位置：`tools/camera_probe.cpp:15,25`，`camera_worker.hpp:13`，`camera_worker.cpp:152–153,181`。

probe 仅传入 device、model、cuda 三个字段，而 `CameraSettings::record` 默认 `true`。实际 worker 会在当前工作目录下创建 `camera_recordings/` 并录制，但成功提示声称 `no image files saved`。

实施要求：probe 显式关闭录制，保留生产相机原有的默认录制行为。验证 probe 运行前后不产生录制目录或文件。没有摄像头/模型时，只能报告此项未完成设备验证，不能声称已实测通过。

### R7：大文件的职责边界不清晰，但不宜同时重写算法

`radar_gui.cpp` 有 4,699 行，混合布局、设备操作、实时/离线模式、目标选择、轨迹绘制、日志、协议导出与 ROS 编排；`target_tracking.cpp` 有 3,147 行。

实施要求：首先进行保行为的文件归位，再提取主窗口中的布局与控制快照/诊断输出职责。跟踪算法本轮以移动和保持行为为主，不要求拆开卡尔曼、重捕获等内部状态机。避免把目录整理扩大为一次算法重写。

## 8. 验收标准

### 8.1 结构与构建

- 根目录不再平铺业务 `.cpp/.hpp/.cu` 或生成的 Qt UI 头。
- 活动源码只有一套当前 tracker、association、DSP 和视觉关联实现。

- CPU 配置不要求 Qt、CUDA、ROS；WSL GUI 可使用 CPU DSP；Jetson 配置保留 CUDA。
- 工具与测试通过 target 或明确参数定位二进制，不再猜测多个旧 build 路径。
- `.ui` 的修改可由正常构建生成到界面，源码目录没有手工维护的生成头。

### 8.2 必须保留的现有验证覆盖

按届时迁移后的路径运行，原有测试名称可重命名，但以下覆盖不能因清理而消失：

- 雷达：配置验证、DoA 稳定性、IQ/Doppler、CUDA FFT contract、DCA 控制、组帧和采集可靠性。
- 跟踪：tracking_regression、v3_stability、v2158_tracking、人工预选/连续确认、丢失与重捕获、帧运动上下文。
- 协议：ODM8 编解码/IPC、21 列跟踪记录、原子 metadata、重复帧/过期帧、session/UID/selection_epoch 与视觉许可。
- 视觉：人工关联、人物短期连续性、相机录制与回放、相机面板行为。
- GUI：协同布局、目标选择、传输、反复创建/退出、ROS 面板与停止/清理流程。
- ROS/Python：bridge runtime、odom transport、overlay verification、GUI runtime 和所属进程清理。
- 离线：录制帧索引 CLI、输入路径、里程计回放与边界条件；fixtures 必须迁移保留。

先运行已有相关测试；新增验证只覆盖本次真正改变的行为，不为纯移动编写机械重复测试。

### 8.3 操作与数据

- 旧本地配置迁移不丢值；新录制/日志写入数据目录。

- camera_probe 在有硬件验证时不生成图像录制文件。
- 没有硬件、ROS 或模型时，明确列出未验证项；不能用 headless GUI 测试代替底盘闭环验收。
